## 1. 数据管线与真值来源

### 1.1 语料与工具

- 语料：Rewrite HD Terra 线剧本 `seen08000.dat`（二进制），反汇编为
  `structure/seen08000.dat.txt`（**271,669 行**，Siglus 引擎字节码 + 重构表达式注释）。
- 反汇编工具：SiglusSceneScriptUtility（`-x --disam`）。
- 解析管线：`src/parse_disasm.py`，产出三个真值文件：
  `data/lines.jsonl`（行级台词，11,033 条）、`data/scenes.jsonl`（检索单元 chunk）、
  `data/choices.json`（选择肢节点）。旧版输出备份在 `data_v1/`，新旧对照即第 5 节的回归 diff。

### 1.2 本项目数据质量的"奢侈之处"与常态差距

反汇编提供了**完整、确定、可零成本验证的行级真值**：说话人（CD_NAME）、分支结构
（`c[810]` 比较链）、终点（`return_to_menu`）都可由字节码直接判定。这使
"规则 + 断言"这套最便宜的质检手段在本项目即可覆盖全部已知错误类别。

真实语料（PDF 解析、网页抓取、OCR、LLM 抽取）错误类别完全相同，但没有这种真值，
因此本项目的分层防御（§4）在真实场景下每一层都需要加强，而不是可以省略。
这一点写进报告可以同时支撑"数据来源与清洗规则"（任务书四.1）和"局限"（第六节）。

### 1.3 引擎的两套选择机制（后续多个案例的根因）

| 机制 | 调用形态 | 返回 |
| --- | --- | --- |
| 剧情选择（两段式） | `selbtn_ready(10, 选项…)` 注册 → `selbtn_start()` 挂起 | 选中下标存入 `global.c[810]` |
| 一次性选择（战斗等） | `selbtn(10, 选项…)` 单调用 | 返回值直接赋给 `global.c[810]` |

全文件共 **52 个选择点**（47 两段式 + 5 一次性），全部把结果写入同一变量 `c[810]`；
其中 **31 处** `CD_GOTO_FALSE ; cond=(global.c[810] == N)` 比较门构成 if-else 链，
**10 个**选择点存在真分支（5 剧情 + 5 战斗），其余 42 个为伪选择肢（§2 案例 3）。

## 2. 失败案例（≥3 个，逐一归因）

> 每个案例按"现象 → 发现过程 → 根因归因 → 修复 → 验证"记录。
> 五个案例分属 **四类错误**：切分策略缺陷、管线覆盖偏差、口径假设错误、控制流语义误读
> （另有顺序真值局限一条），满足评分表④"≥3 类错误归因"。

### 案例 1：互斥分支文本线性污染 chunk（切分策略缺陷）

- **现象**：v1 的 `scenes.jsonl` 中，"捕捉她/除掉她/逃走"选择肢（rfid 5161）所在的
  选择前 chunk（c167）尾部同时出现"…试着捕获。"（捕捉她线）与"不除掉的话…"
  （除掉她线）——两条**互斥时间线**的首句被当作连续叙述拼在一起。
- **发现过程**：人工抽查 chunk 文本时注意到语义矛盾，回溯反汇编定位到三处机制。
- **根因归因**（两层叠加）：
  1. v1 切分只依赖"label 变化 / 源行号跳变"两个信号；而 `<L128>` 标签行在文件顺序上
     位于捕捉她文本**之后**（标签放在跳转目标处），检测不到 ==0 分支体的起点，
     源行号前跳又只有 4 行，触发不了分段阈值 40；
  2. "不除掉的话…"虽因 label 121→128 触发了新分段，但整段仅 6 字，低于
     `MIN_CHARS=40`，被碎片合并**无守卫地塞回前一个 chunk**。
- **修复**：v2 在解析循环中加入分支状态机（详见 §3.2）：比较门处强制开新段；
  碎片合并增加"branch_ids 相同才可并"守卫。
- **验证**：v2 中该位置切分为 c168（选择前，branch=null，以"我是狩猎者啊――"收尾，
  choices:[20] 挂载于此）、c169（[0]，"…试着捕获。"）、c170（[1]，"不除掉的话…"）；
  断言"chunk 内分支一致"全部通过。
- **残余局限**：独占句各自成 6 字小 chunk，低于长度美学阈值；语义正确性优先于尺寸，
  未做同分支相邻小段合并。

### 案例 2：选择肢节点缺失——5 个一次性选择未收录（管线覆盖偏差）

- **现象**：v2 上线后人工核对发现，反汇编 87911 行的
  `selbtn(10, "飞行道具", "近距离攻击武器")` 在 scenes.jsonl 有 branch_ids 标注（c107），
  choices.json 却没有对应节点；排查后确认共 **5 个**（另 4 个为从正面/用匕首/瞄准要害/
  持续发动进攻）。
- **发现过程**：跨工件一致性检查——同一场战斗的区域一边有分支标注、一边无节点，
  两处说法不一致即为错误信号。
- **根因归因**：管线只认两段式 `selbtn_ready` 的模式假设，未覆盖一次性 `selbtn(`
  调用；且此前一次快速扫描的正则把首参写死为 `10,`，漏掉首参为 `11` 的用例
  （4 个被误报为 5 个缺口中的实际数字差，说明**核对脚本自身也要过断言**）。
- **修复**：新增 `re_selbtn_cmd` 收集调用行（rfid 直接取自调用行 read_flag），
  赋值行接管区域；全部选择肢增加 `kind` 字段区分两种机制。
- **验证**：choices 47 → 52，5 个新节点全部 `has_branch=true` 且选项→chunk 映射正确
  （如 seq=5：选项 0 → c107+c108，选项 1 → c108）；三断言通过。
- **副作用（须在报告中声明）**：选择肢 seq 整体位移（"捕捉她/除掉她/逃走" 15 → 20），
  chunk 的 `choices` 引用已同步重编；下游引用旧 seq 的地方需同步。

### 案例 3：42 个伪选择肢被误当分支节点（口径假设错误）

- **现象**：v1 文档假设"47 个选择肢 = 47 个分支节点"；实测仅 10 个存在
  `c[810]` 读取链，其余 42 个选完后**直线续播**，返回值从未被读取。
- **发现过程**：全量扫描 31 处比较门并归属到最近写入点，发现绝大多数选择点
  后 0 处比较；抽查文本证实（"阻止他们/不阻止他们"选完照样播放
  "…必须要阻止他们不可。"）。
- **根因归因**：把"界面上有选项"等同于"剧情分叉"。游戏侧佐证：伪选择肢实际只有
  一个选项可点（灰化由引擎 UI 层处理，`selbtn_ready` 签名中无 enabled/disabled
  标志，数据侧不可见）；数据侧可得的最好判据即"有无 `c[810]` 读取链"。
- **修复**：choices.json 增加 `has_branch` 布尔标注（10 真 / 42 伪），
  真分叉附带 `gate_values` 与选项级 `branches`（chunk 映射 + outcome）。
- **验证**：与游戏表现一致；选项后果类问题从"47 个假节点"变为真实拓扑
  （1 个带文本分歧的剧情分叉 + 5 个战斗分叉 + 42 个伪选择）。
- **残余局限**：数据侧无法区分"单选伪选择"与"多选但后续相同"，最终口径
  依赖游戏侧人工观察（见 §6 AI 使用声明的边界）。

### 案例 4：死代码跳转误导分支归属（控制流语义误读）

- **现象**：初次重建"捕捉她/除掉她/逃走"分支结构时，曾依据
  `CD_GOTO L127 -> 000A200B`（000A1FCC）把 c173 起的"…除掉什么的根本做不到。"
  判定为三线汇合点；游戏实测该位置是**逃走线独占**内容，捕/除两线在
  "对。青春这玩意儿，不就是应该去专心地去享受的吗。"（000A1678，rfid 5242）后
  直接 Bad End 回主菜单。
- **发现过程**：人工游玩观察与数据推断冲突 → 回查字节码，在 000A1FAA 处发现
  `syscom.return_to_menu(0,0,…)`：该调用不返回，其后 000A1FCC 的 `GOTO L127`
  是编译器为 if 链补的**不可达死代码**。
- **根因归因**：控制流重建把"地址顺序相邻"当成了"运行时可达"，未处理
  终点指令之后的死代码。
- **修复**：状态机增加两条规则——终点命令（`return_to_menu`/`end_close`）标记
  terminal 并**清空汇合标签的跳转来源**（死分支的跳转作废）；GOTO 之后到下一
  标签之前整体视为死区，不更新状态。
- **验证**：全文件恰 2 处终点——中段 1 处判为 `bad_end`（c173，branch [0,1]），
  文件末尾 1 处（271,666 行，紧跟 CD_EOF）判为 `route_end`（c483）；
  逃走线正确归属 c174 起 26 个 chunk（[2]）。
- **方法论教训（可写进报告④）**：判断分支归属必须以**终点命令**截断，
  而不是以 GOTO 目标当汇合点；"数据里看起来连续"不等于"运行时会到达"。

### 案例 5（局限）：read_flag 顺序 ≈ 脚本顺序 ≠ 游玩时序

- **现象**：行级真值的 rfid（已读事件号）在分支区段内与游玩时序不一致
  （捕/除线的 rfid 5162–5242 与逃走线的 5243+ 在文件中线性交错，游玩时互斥）。
- **根因归因**：rfid 是"已读标记计数"而非时间戳；线性文件顺序天然无法表达
  互斥时间线。此类**顺序真值**的边界必须在构造时序类评测题时显式处理。
- **处置**：时序题构造规则中排除 5 个分支影响 chunk（c106–c108、c169–c173），
  或人工核对后入库；这条局限已写入项目知识文档，属于**已知且已对齐**的口径。

## 3. 课程原理点的实验证据素材

> 任务书要求：原理点必须"用自己实验的证据"解释，只复述概念不算。
> 本节给出两个原理点的现成证据 + 可补跑的小实验设计。

### 3.1 原理点 9（第 15 讲）：RAG 的"召回是上限"——chunk 质量封死召回上限

**原理陈述**：检索召回的语料单元质量决定答案上限；重排与生成只能在下限之上挑选，
无法凭空补全缺失或剔除深度污染。

**本项目证据**（结构性证据，无需跑模型即可论证）：

1. **污染封死上限**：v1 的 c167 同时含互斥分支首句。对"选了除掉她之后发生了什么"
   这类查询，该 chunk 是**主题上最相关**的检索单元——稠密检索会召回它（语义相似），
   cross-encoder 会给高分（内容切题），但**任何模型都无法从混合文本中读出正确归属**。
   上限在 chunk 构造时已经确定。
2. **缺失即无界**：5 个战斗选择未收录时，"武器选择"类问题的正确证据**不在索引里**，
   召回率结构性为 0；任何检索参数调优（top-k、相似度阈值）都无法恢复。
3. **元数据决定可答性**：c173 的 `terminal=true, ending=bad_end` 与 c174 的
   `branch_ids=[2]` 使"这个选择会进 Bad End 吗"从不可答变为可答。

**可补跑的对比实验（建议写入报告⑤，同时满足"≥1 组参数对比"）**：

- 语料版本消融：v1（污染+缺节点）vs v2 语料，固定 BM25 检索器与同一组
  "选择肢后果"类问题（如 5—8 题，人工构造金标 chunk），对比 top-5 命中率。
  预期：v2 在分支后果类问题上显著更高，其余问题持平（分支影响文本仅 0.8%）。
- chunk 大小消融：`parse_disasm.py` 的 `MAX_CHARS`（500 → 300）重跑对比，
  验证"召回是上限"与 chunk 粒度的交互。

### 3.2 原理点 10（第 14—15 讲）：评测协议与金标口径——真值结构的口径错误会污染整个评测集

**原理陈述**：评测结论的可信度受限于金标口径；口径错误是系统性错误，
不会被指标平均值稀释。

**本项目证据**：

1. 时序题若按 rfid 顺序自动构造金标，分支区段会产出**时序上为假**的题目
   （把互斥时间线当先后事件），且错误随题目数量线性复制——案例 5。
2. "47 个分支节点"口径若不修正，图谱分支扩展会在 42 个伪选择上引入错误路径；
   评测集越大，错误口径的放大效应越强。
3. 因此评测协议必须包含**口径审计步骤**：先修真值结构（v2 + 断言），再冻结评测集
   ——这正是任务书"评测集本身进版本管理"要求的实践动机。

### 3.3 分支状态机的形式化（可作报告④"关键技术点"）

v2 在解析循环中加入按文件顺序推进的状态机，5 条规则对应 5 类字节码形态：

| 规则 | 触发指令（正则形态） | 状态动作 |
| --- | --- | --- |
| R1 分支门 | `CD_GOTO_FALSE … cond=(global.c[810] == N)` | 强制开新段；branch_ids={N}；收集 N |
| R2 块尾跳转 | `: CD_GOTO L(\d+)` | label_srcs[L] ∪= branch_ids；其后至下一标签为死区 |
| R3 标签行 | `^([0-9A-F]+): <(L\d+…)>` | 跳转来源分支并入 fall-through（汇合点重建） |
| R4 终点命令 | `syscom.return_to_menu` \| `global.end_close` | 标记 terminal；**清空 label_srcs**（死分支跳转作废）；branch_ids=null |
| R5 碎片合并守卫 | （合并阶段） | 仅 branch_ids 相同的碎片可并入前 chunk |

配套三条自动断言（把"人工巡检"变成回归检查）：
① chunk 内 branch_ids 一致；② 终点后必须换分支/换 chunk；③ 分支门 N ⊆ 选项下标。
本次运行断言全部通过；断言失败即转人工——这是"自动检查够不到的才用人"的边界实践。

## 4. 方法论边界：检索侧方法为何不能替代数据质量（支撑报告②⑥）

核心结论：**稠密检索、cross-encoder、图谱增强都是相关性优化器，不是真值校验器**。

| 方法 | 缓解什么 | 放大/掩盖什么 |
| --- | --- | --- |
| 稠密检索 | 表层标注错误（同义改写不再致命） | 语义污染照样嵌入成流畅向量，**自信地召回错误上下文** |
| Cross-encoder 重排 | 粗切分导致的无关召回 | 只判断相关性不判断事实性，主题相关但归属错误的 chunk 照样高分通过 |
| 图谱增强 | 结构错误最易暴露（悬空节点、度异常）；多跳可交叉验证 | 一条错误边污染所有经过它的路径（错误传播） |

以案例 1 为例：c167 无论过稠密检索、重排还是图谱都会被放行——三层防线对
"看起来合理的错误"全部失效，而 LLM 生成端还会加重（生成器天然信任流畅上下文）。
有效的补强是**多路冗余**（BM25 ∥ 稠密 ∥ 图谱一致=可信、分歧=复查信号）与
**查询时校验**（NLI/引用一致性核对），后者把错误处理挪到查询时，代价是延迟与算力，
且只救答案、不治语料。

错误发现的完整分层（生产对应）：结构断言 → 跨工件一致性 → 版本 diff 回归 →
统计漂移 → 定向抽样审计 → 评测/反馈驱动。错误处置按
"错误代价 × 频率 vs 修复成本"排序：源头修复重跑（确定性管线最便宜）> 隔离过滤 >
软降权 > 人工队列 > 容忍并记录（交给 eval 量化影响）。
